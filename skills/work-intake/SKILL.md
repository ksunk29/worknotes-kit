# 요구 정리와 질문 설계

1. 구현하지 않고 읽기만 한다. README·`docs`의 문서와 요청 메일은 **끝까지** 읽는다(조건이 뒤에 있을 수 있다). 설정·시작 코드·보조 파일(휴일·담당자 목록 등)도 요구에 영향을 주면 읽는다. 큰 데이터 파일은 통째로 읽지 않고 이름·헤더·몇 줄·전체 행 수를 본 뒤, 이상 징후(빈 값, 중복, 형식 불일치, 날짜 범위)를 검색이나 간단한 집계로 확인한다. 읽다가 다른 파일이 필요하면 그 파일도 읽고, 읽은 파일 목록을 정리 문서에 적는다.
2. 아래 네 가지로 나눠 `TASK.md`에 적는다.
   - **명시된 요구**: 문서에 그대로 적힌 것 (출처 파일 표시)
   - **미확인 정보**: 문서에 없지만 결과를 바꿀 수 있는 것
   - **가정**: 답을 받기 전까지 잠정으로 구현할 기준. "확인 전 가정"이라고 코드 주석·문서에 표시한다. 필수 필드·인터페이스는 명세를 따르고, 값을 알 수 없으면 명세가 허용하는 미확정·오류 상태로 처리하며 필드를 채우려고 사실이나 데이터를 만들어내지 않는다
   - **핵심 가정**: 가정 중 틀리면 결과 전체가 무너지는 것은 따로 표시하고, 큰 작업을 시작하기 전에 담당자 질문이나 실제 데이터 확인으로 먼저 검증한다
   - **완료 기준**: 무엇을 어떻게 확인하면 끝인지
3. 미확인 정보마다 담당자에게 물을 질문을 만든다.
   - 사소하고 구체적인 것부터, 한 번에 하나씩
   - 관점: 누가 쓰나 → 입력 데이터의 이상한 점 → 계산·판정 기준 → 예외·제외 → 출력 형식 → 앞으로 반복·변경
   - 구현 방법을 묻지 않는다. "해야 할 일을 번호로 알려 달라"는 요청은 하지 않는다.
4. 답변을 받으면 `TASK.md`의 질문·답변 표에 요지를 기록하고 해당 가정을 확정하거나 고친다. 답이 없는 항목은 "미확인"으로 남긴다.

산출물: 요구 / 미확인 / 가정 / 완료 기준 / 질문·답변. 과제가 요구하는 문서가 있으면 그 안의 섹션으로, 없고 과제가 클 때만 `TASK.md`로 쓴다. 작은 요청은 채팅으로 답한다.

하지 않을 것: 확인되지 않은 업무 기준을 사실처럼 코드에 넣기, 질문을 한꺼번에 던지기.
